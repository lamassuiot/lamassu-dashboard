# Vendored unkernel web shell

The browser shell of the public unkernel page, ported to run over the published SDK.

- Source: https://github.com/pithings/unkernel, directory `web/src`
- Release: `v0.2.0-261119-97d7945` (npm `unkernel@0.2.0-261119-97d7945`)
- Commit: `97d7945`
- License: MIT, Copyright (C) 2026 Pooya Parsa. Each vendored file keeps its SPDX header. The kernel (`unkernel.wasm`) is GPL-2.0-only; see `public/terminal/unkernel-GPL-2.0.txt` and `public/terminal/unkernel-MIT.txt`.

This folder is excluded from ESLint (`eslint.config.mjs`) and keeps upstream's relative `./x.ts` imports (`allowImportingTsExtensions` in `tsconfig.json`). Keep upstream's style here so a later re-sync stays a small diff.

## Vendored unchanged or nearly so

`boot.ts`, `config.ts`, `kw.ts`, `session.ts`, `data.ts`, `net.ts`, `store.ts`, `ui.ts`, `windows.ts`, `shortcuts.ts`, `bottom.ts`, `components/{Bar,Panel,Options,Keys,icons}.tsx`. `style.css` is `unkernel.css`, rewritten to be scoped (see "CSS scope"); `components/{About,Overlays}.tsx` changed only in how their dialogs open (see "Dialogs and fixed positioning"). `components/App.tsx` is upstream's, cut down (see below).

## Local files (not upstream)

- `mount.tsx`: replaces upstream's page entry `main.tsx`. `mountUnkernel(root, { wisp })` reads the config, sets up the UI, runs upstream's preflight and starts `boot.ts` inside `root`, and returns a session with `stop()`, `sendScript()` and `focus()` (see "Mounting and teardown").
- `sdk.ts`: replaces upstream's `sdk.ts`. Re-exports what the vendored files import from `unkernel/web` (the published web build), and provides `kernelUrl` (`unkernel/unkernel.wasm?url`), `kernelSmpUrl` (always `null`: the npm package ships only the single `unkernel.wasm`, no SMP kernel, so `?cpus=` always boots one CPU) and `distros` (one entry, `debian`, served from `/terminal/debian.erofs`). Also re-exports `BlockDevice`, `DistroDisk`, `DownloadProgress`, `DiskSnapshotState` and `Kernel`, which upstream's `export *` gave `boot.ts` and `session.ts`.
- `build.ts`: `KW_BUILD`, in place of upstream's `__KW_BUILD__` define (read by `components/About.tsx`). `linux` is the release in the `Linux version` string of the package's `dist/unkernel.wasm` (`strings dist/unkernel.wasm | grep 'Linux version'`: `7.3.4+` for this release); update it with the package.
- `sdk.test.ts`: pins the adapter to what the npm build really exports, the debian image's size to the file in `public/terminal/`, and `build.ts`'s Linux release to the packaged kernel.
- `mount.test.tsx`, `shortcuts.test.ts`, `config.test.ts`: the mount, teardown, Send to terminal, scoped shortcuts and settings tests (the SDK and wterm are faked).

## Mounting and teardown

`mountUnkernel(root, { wisp })` (`mount.tsx`) waits for a session that is still stopping, then runs upstream's `main.tsx` flow inside `root`: `readConfig("", loadSettings(), { wisp })` (never the page URL, see below), `createKW()`, `createUi()`, React (`components/App.tsx`, rendered with `flushSync` so `boot.ts` finds `#term`), the preflight with `checkSupport()` (a browser without WebAssembly, BigInt or JSPI gets the reason in the Errors panel and the kernel is never downloaded), then `start(root)`.

Callers: React forbids `flushSync` inside a lifecycle method (an effect), so `mountUnkernel` must not be called synchronously from one. `UnkernelTerminal.tsx` calls it a microtask later, and takes its mounts one at a time (a mount waits until the previous one resolved, and a mount whose effect was already cleaned up is skipped or stopped at once), so a StrictMode mount, stop and mount, or a quick close and reopen, ends with exactly one live session; `stop()` is idempotent.

`session.stop()` (also what a restart does to the old run):

1. once user space runs, asks the guest to sync (at most 3 s) first: the SDK stops a booted kernel as soon as the signal given to `createKernel()` aborts, without a clean shutdown, so the sync must come before the abort;
2. aborts the boot (`createKernel()` and `loadKernelModule()` get the signal; a pending resume question is answered "no") and stops the kernel if one exists (once, also when it finished booting just after the abort);
3. waits for the boot to settle (at most 5 s for a step that takes no signal, such as opening IndexedDB; whatever such a step attaches later is still let go when it settles);
4. lets go of the data disk: detach, wait for the last save, close the store, release the lock (and the lock a data disk Reset or Import took when the run had none, which upstream's page reload used to free), so the next mount opens the persistent disk instead of an unsaved copy;
5. closes terminal windows 1 to 9 and destroys window 0's wterm, removes the boot's listeners and intervals, the `globalThis.term` / `vm` / `kernel` debug globals, then unmounts React (which removes the UI's listeners).

Listeners on `window` / `document` while mounted, all removed by `stop()`: `keydown` (capture, `shortcuts.ts`), `visibilitychange` and `pagehide` (`boot.ts`), `resize` and `visualViewport` `resize` (`App.tsx` `useBottom`), on phones `resize`, `visualViewport` `resize`, `focusin`, `focusout` (`useKeyBar`), and while the `⋯` menu is open `pointerdown` and `keydown` (`Bar.tsx`). The pinch (`touch*`, `gesture*`) and wterm's own listeners are on elements inside `root`.

Where upstream reloads the page (Reboot, Resume, a data disk import or reset, the one-CPU fallback), the session stops the run and mounts a new one in the same `root` (`KW.reload`). Reboot passes the settings it saved, which apply even where `localStorage` refuses them.

The page URL is neither read nor written. Upstream lets URL parameters (`?wisp=`, `?append=`, `?distro=`, `?mem=`, ...) override the saved settings for one load; in the dashboard the URL is the dashboard's own, so a crafted link (for example `/ra/x?wisp=wss://evil.example/`) could route the guest's traffic, EST enrollment included, through someone else's proxy, or change the kernel command line, and Reboot would then save it. `mount.tsx` therefore passes an empty query to `readConfig()`: settings come only from Options (`kw.settings`) and the operator's default. Upstream's URL-only test hook `?simulate=` is unavailable for the same reason.

`session.sendScript(script)` waits until the state is `running` (across restarts; a boot failure, state `error`, rejects; while halted it keeps waiting for Reboot or Resume), then runs `/bin/sh -ec 'umask 077; dir=$(mktemp -d /tmp/est-enroll.XXXXXX); cat > "$dir/enroll.sh"; printf %s "$dir"'` with the script as stdin on the kernel handle (`KW.ready()`) and resolves with `cd <dir> && sh ./enroll.sh`. The script is never run. A non-zero exit, a directory that does not match `^/tmp/est-enroll\.[a-zA-Z0-9]+$` or a failed exec rejects with `Error("Unable to prepare the enrollment script.")`. A newer call, or `stop()`, rejects the pending one with an `AbortError` (its exec is aborted).

## Wisp default

`LAMASSU_TERMINAL_WISP_URL` reaches `readConfig()` as `defaults.wisp` and applies when no saved setting names `wisp` or `net`. The Options UI cannot save an empty `wisp` (`nextSettings()` drops custom servers left empty), but a hand-edited `kw.settings` could hold one: an empty value counts as unset, so the operator's default still applies (it is not a way to switch upstream's servers back on; `wisp=0` or Network Off disables the network). Servers that came from the default show as the default in Options and are never saved by Reboot, so a later change of `LAMASSU_TERMINAL_WISP_URL` reaches every browser.

## URLs and the dashboard's base

`kernelUrl` is `new URL(unkernel/unkernel.wasm?url, location.href)` and `config.ts` uses its `pathname`. Vite emits the `?url` asset with the build's `base` already applied (`/assets/unkernel-<hash>.wasm` with the default `base: '/'`, which the dashboard uses; nginx serves `out/` at `/`), so it is right wherever the page itself is. The distro URL `/terminal/debian.erofs` is root-absolute: if the dashboard is ever built with another `base`, it must become `${import.meta.env.BASE_URL}terminal/debian.erofs` (the old `LinuxTerminal` did that); `sdk.test.ts` pins today's value.

## CSS scope

Upstream's `style.css` imports Tailwind (a second `@import "tailwindcss"` would apply the reset again, page-wide), imports the Geist fonts, defines an `@theme` with colour tokens, and styles `:root`, `html` and `body`. `unkernel.css` is imported only by `UnkernelTerminal.tsx` (so it loads with the lazy chunk) and works like this:

- It starts with `@reference "../../../app/globals.css"`: the dashboard's Tailwind theme is available to `@apply` (the `.btn`, `.field` classes keep upstream's `@apply` lines) and nothing of Tailwind is emitted a second time.
- Every rule of upstream (`:root`, `html, body`, `.btn`, `.field`, `.select`, `.slider`, `#panel`, `#scrim`, `#terms .wterm`...) is under `.unkernel-root`, the element `UnkernelTerminal.tsx` mounts into. The `--bar-h`, `--sb`, `--sl`, `--sr`, `--st` and `--sc` variables are defined there.
- Colour utilities: the vendored components use `bg-bg`, `text-fg`, `border-line`... Tailwind only generates a utility for a theme token, so `src/app/globals.css` has a short `@theme` block with the tokens the dashboard does not use: `bg`, `surface`, `hover`, `line`, `line-strong`, `fg`, `faint`, `ok`, `warn`, `err`, `off` (grep found no use of these names in the dashboard). That adds about 35 small rules to the entry stylesheet, none of which an existing rule depends on.
- `muted` and `accent` are dashboard tokens too (`text-muted`, `bg-accent` are shadcn's). They are not redefined globally. The dashboard declares them in an `@theme inline` block, so Tailwind compiles its utilities to the source variables (`.text-muted { color: var(--muted) }`, `.border-muted`, `.bg-accent`, `.ring-accent/40` and `.outline-accent` read `var(--muted)` / `var(--accent)`), not to `var(--color-muted)`. So `.unkernel-root` sets `--muted: #a1a1a1` and `--accent: #52a8ff` (the source variables, which is what the vendored utilities read), plus `--color-muted` / `--color-accent` pointing to them for `unkernel.css`'s own `var(--color-*)` uses. The same class is the dashboard's colour outside the root and the shell's inside it. Verified in a built page (computed styles in headless Chromium, dashboard light and dark theme values, with and without the lazy stylesheet): outside the root `text-muted` and `bg-accent` are identical either way; inside, they are `rgb(161, 161, 161)` / the shell's.
- `--font-mono` is also set on `.unkernel-root` (the dashboard's `@theme inline` block does not list it, so `.font-mono` reads `var(--font-mono)`; the other tokens set on the root, `--muted` and `--accent`, are the only inline ones), to `var(--font-jetbrains-mono)` first (the dashboard's font; Geist is not added), and wterm's `--term-font-family` follows it. `h1`..`h6` inside the root inherit their font (the dashboard sets its headline font on every heading).
- Checked on the production build: the entry stylesheet differs from the build before only by those new rules and the new theme variables (no existing rule changed); the lazy stylesheet has only wterm's own `.wterm` / `.term-*` rules and `.unkernel-root ...` rules (no reset, no `:root`, `html`, `body`, `*` rule except Tailwind's `@property` fallbacks, which repeat the entry's).
- Upstream's `:root.mac-window` rule (set by upstream's page entry on a macOS window) is not carried over: nothing sets it.

## Dialogs and fixed positioning

Upstream's panel (`#panel`, `#scrim`), the paste dialog and the toast are `position: fixed`, and the confirm and About dialogs are modal `<dialog>`s (`showModal()`). In the dock all of them would cover the whole dashboard.

- `.unkernel-root` has `contain: layout paint` (and `position: relative; overflow: clip`): it is the containing block for its `fixed` descendants, so the panel, scrim, paste dialog and toast stay inside the dock without changing their classes, and their z-indexes live in the root's own stacking context. Where upstream used the viewport (`100vw`, `100dvh` in `#panel`) the CSS uses the root (`100%`).
- A modal `<dialog>` goes to the browser's top layer, which no containing block can hold. The confirm dialog (`Overlays.tsx`) and About (`About.tsx`) open with `show()` (non-modal) instead of `showModal()`, and `.unkernel-root dialog[open]` centres them in the root, with the shade drawn as a very large `box-shadow` that the root clips. That rule is `position: fixed`, not `absolute`: About is rendered inside the status line (`#bar` is `relative`), so `absolute` centred it in the 28 px bar (found in the browser check); `fixed` resolves against the root's `contain: layout` whatever the dialog's parent. What the browser did for a modal is done by the shell: Esc cancels (confirm answers no, About closes); while the confirm dialog is open the other children of the root (the app, the panel; not the toast) are `inert`; focus returns to where it was when the dialog opened (About: the terminal when that was nothing; `showModal()` restored it, `show()` does not, and upstream's `onClose` check alone left it on the hidden Close button). A confirm opened by a mouse click on the status line returns the focus to nothing, as upstream (the click blurs the button first): click the terminal, or use the prefix (`Ctrl-A r`), which returns it to the terminal. What is lost: the rest of the dashboard stays usable while one of them is open (the dock is not modal either), and a click on the shade no longer closes About (the Close button and Esc do).
- A short dock can be shorter than About (about 340 px): the dialog is held to the dock (`max-height`) and its body scrolls (`#about[open]` is a flex column, its body `overflow-y: auto`; the title on the border stays visible). The root is `overflow: clip`, not `hidden`: an `overflow: hidden` box can still be scrolled, and focusing About's Close button in a short dock scrolled the root by 72 px, leaving the whole shell (status line included) shifted up after About closed (found in the browser check).

## Checked in a browser

On 2026-11-20 the shell was driven in Chromium 156 (Playwright) on the dev server and on the production build (`vite preview` of `out/`, kernel at `/assets/unkernel-<hash>.wasm`), over the real SDK and image: boot (under 1.2 s to the prompt, stage lines and Pip's summary), the status line, `+` and `×`, `Ctrl-A ?`, Esc, Options saved by Reboot, the confirm and About dialogs inside the dock, the `⋯` menu below `sm`, three close and reopen cycles (one during boot: no console errors, no Web Lock left, `/data` written just before closing still there at the next boot, "saved in this browser" every time), a StrictMode mount (one session, one lock), Suspend then close and Resume, the guest network over the default Wisp server, Send to terminal (the file is `-rw-------` in a `drwx------` `/tmp/est-enroll.*`, never run), and a browser without JSPI (no `unkernel.wasm` or `debian.erofs` request). Chromium 156 cannot turn JSPI off (`--js-flags=--no-experimental-wasm-jspi` and `--disable-features=WebAssemblyJSPromiseIntegration` leave it on), so that check deletes `WebAssembly.Suspending` and `WebAssembly.promising` before the page runs. Defects found and fixed then: About centred in the status line (`position: fixed` above), About leaving the focus on its hidden Close button, the root scrolled by About's focus in a short dock (`overflow: clip` above), and About's "Linux ?" (`build.ts`).
